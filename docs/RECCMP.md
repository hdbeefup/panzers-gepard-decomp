# reccmp: lifted functions vs the HD PANZERS.exe

This report covers master `0f90874` (census 1613 lifted / 1317 SWINE-shared / 361 stubs),
a Release build with `-DPZ_MENU_WORLD=ON` from VS 2026, and reccmp 0.1.0. The original is
the 2016 HD `PANZERS.exe`, sha256 `953ab3c6…3741`, built with VS2015 Update 1.

This is a functional decomp, not a matching one, so these scores measure drift. They don't
set a byte-match target. Rerun everything with `python tools/reccmp_run.py` (see the README).

### How the mapping is built

`reccmp_gen.py` reads the PDB through reccmp's own cvdump wrapper. That gives every
`S_GPROC32` function with its address, size, decorated name and line range. For each
`// PANZERS 0xADDR` marker it then picks one of these:

- **following**: the first PDB function in the same file that starts after the marker,
  **has the same name** as the identifier in the source that follows the marker (the last
  component, with Win32 `A`/`W` macro renames allowed), and has no other marker in between.
- **enclosing**: an in-body `(Name, partial)` marker inside the function it names, for
  example `SBoard::SBoard` or `SGepard::Initialize`.

A marker that matches neither is left out. If two markers carry the same HD address, a
plain marker wins over a `(piece)` marker, and after that the larger body wins. reccmp
pairs the rows by the **decorated symbol**, so overloads such as the two `SWorld::CreateUnit`
and `SPropertyStruct::Get*(int,…)/(const char*)` resolve correctly.

| markers | count |
|---|---|
| mapped (CSV rows) | **1199** (1196 following, 3 enclosing) |
| no PDB body under that name: inlined everywhere, folded by /OPT:ICF, or dropped by /OPT:REF | 326 |
| the next marker comes before the body (the body was inlined) | 25 |
| no identifier found after the marker | 11 |
| second marker for an HD address that is already mapped | 52 |

All 1199 CSV rows matched in reccmp (the 1200th entry it reports is `WinMainCRTStartup`).
Every marker and how it resolved is listed in `build/reccmp-mapping.tsv`.

### Verification

- **All 1199 addresses** are function entries in a fresh Ghidra auto-analysis of the HD exe.
  The one exception is `0x6875a0 MilesStreamCallback`, a callback used only through a
  pointer, which Ghidra missed. It sits right after int3 padding and starts with a prologue.
- 1187/1199 addresses are preceded by `int3`/`ret`/`nop`. The other 12 come right after
  another function with no padding.
- **I checked 10 functions by hand**, comparing the original's first instructions against
  our body and the source signature. In all 10 the right body was paired:

| HD | ours | evidence |
|---|---|---|
| 0x6abc60 SScene::GetAmbientLight | identical | `lea eax,[ecx+0xd8]; ret` in both |
| 0x687550 SMilesConcert::StopStream | identical | same 9-instruction prologue and member tests |
| 0x6e9690 SParticles::SetAlphaScale | same code, field +0x10c vs our +0x100 | layout drift only |
| 0x6c27f0 ArgbToFloat4 | same constants and shifts | HD passes `o` in a register (see below) |
| 0x5b5ba0 SUnit::DriverDropLocalPath | same `[ecx+0x1f4]`, `[ecx+0x28]`, `+0x38` array tests | |
| 0x58e1e0 manoeuvre SimpleOut | same frame, `ebx=this` | |

## Why a second score

reccmp 0.1.0 has two weaknesses on this project:

1. It reads the original **with our function's size**, capped at the next mapped address. A
   2-instruction stub gets compared against the first 2 instructions of a 3000-instruction
   original, and still scores 20–40%.
2. On the original side it can only name the 1199 mapped addresses. On our side it names
   every PDB symbol. So every call into SWINE-shared code, and every global, counts as a
   mismatch.

`reccmp_rescore.py` disassembles each pair again with capstone. The original's extent comes
from Ghidra, and ours from the PDB. It replaces every address and call/jump target with a
placeholder and reports these scores:

- `norm`: exact instructions, with addresses abstracted.
- **`regs`**: `norm` with general and xmm registers folded by class. This is the main drift
  measure, because register allocation is most of the VS2015-vs-2026 noise.
- `shape`: the mnemonic sequence only.

Stack and struct offsets and small immediates are kept, because they are real drift.

### Systematic noise (counted over all 1200 pairs)

- **PZ_TRACE** adds a `cmp byte [flag]; je; push; push; call` at the start of 158 of our
  functions. This dominates the score of small functions.
- **/GS**: 247 HD functions have a security cookie. We build with `/GS-`.
- **SEH frames**: 216 HD functions set up `fs:[0]` frames, against 138 of ours, because our
  locals often have no destructors.
- **Calling convention**: the HD exe was linked with LTCG, so static helpers get custom
  register conventions. For example, `Mat34To44` 0x676f60 takes its destination in `ecx` and
  does `ret 4`, and `ArgbToFloat4` 0x6c27f0 takes `o` in `ecx`. Ours are plain cdecl. This
  shows as `shape` 100% next to `regs` around 12%.
- **Layout drift**: member offsets of SWINE-derived classes differ, for example
  SParticles +0x10c/+0x100 and SViewport +0x1b0/+0x140 (docs/ENGINE_DIFF.md).
- **VS2026 codegen**: it vectorises struct copies (`movups`), uses `cmov`, and orders basic
  blocks differently.

## Triage of the worst ~10

I read each of these against the HD disassembly.

**Real behaviour differences (bugs or missing code):**

1. **SWorld::RefreshModels 0x576d80**: 61 vs 1701 instructions. The source calls it an
   "M1 subset" (pose store and refresh). The rest of the HD tick isn't there. It works for
   the menu, but it's missing code for M3.
2. **SUnit::RefreshRepairTarget / RefreshSupplyTarget / ServerRefreshMedic, SPanzersSquadUnit::Hook20,
   SWorld::RefreshFlyingFox, SSingleUnit::UpdateVisuals, SGameLogic::RunTriggers,
   SPUnit/SPBuildingUnit::LoadResources**: entry test plus STUB_LOG. The behaviour is
   missing, and the `PANZERS` marker overstates the lift.
3. **SAnimesh::Lock 0x6d0b40**: HD (47 instructions) locks a vertex buffer. Ours only points
   `Vertices` at the last frame. This works only because our draw path never uses the lock.
   Check it if dynamic meshes are wrong.
4. **STerrain::RenderLate 0x6f33c0**: HD walks flora back to front by camera-yaw octant. Ours
   goes row by row. Alpha-blended flora can sort differently, so this is a real visual
   difference.
5. **STerrainDrawState::Reset 0x687730**: HD writes identity texture transforms at
   +0x6c..+0xe0 and calls 0x6883a0 for the rest. Ours merges both on its own layout, so
   `shape` is 79% but offsets differ. Check that our texture-transform reset happens somewhere.

**Codegen or deliberate restructuring (not a bug in itself):**

6. **SPixie::SPixie 0x6941e0**: the HD 35 KB constructor is mostly the inline property-schema
   build. Ours generates the schema in effectschema.cpp. The score says nothing useful here.
   effectschema.cpp has to be checked on its own (it also isn't UTF-8, and reccmp skips it).
7. **BlockMap_CheckStaticInternal 0x5da050**: HD unrolls each unit size. Ours is one loop,
   checked against every size in the emulator. One deliberate difference: ours warns once per
   size, where HD warns on every call.
8. **SSingleUnit::Init / InitNew**: HD duplicates the crew/children set-up inline in both. Ours
   calls the shared, unmarked `InitCrewAndChildren`, which has no `PANZERS` marker and so gets
   no score. Give that helper its own marker to compare it.
9. **SModel::ComputeNodes 0x6dc7b0** (1585/1213 instructions, shape 34%): VS2026 vectorises
   the matrix copies, and the blocks are ordered differently. Same structure, no evidence of a
   bug. One oddity: ours converts a double (`cvtpd2ps` from `[eax+0xb8]`) where HD stays in
   single precision. That's a possible type mismatch to check.
10. **SSkinnedMesh::DrawShadowSkinned 0x6d0e30**: HD inlines the CPU skinning (and a vertex
    shader path HD never takes). Ours calls FillSkinned 0x6d2200. The structure differs, and
    the behaviour should match if FillSkinned scores well (9%: needs its own look).

There are two more signature-level patterns worth fixing in bulk: the LTCG register conventions
(Mat34To44, ArgbToFloat4 and similar, which are harmless inside our exe) and the PZ_TRACE
prologue. Make PZ_TRACE compile out in a "compare" build to lift every small function's score.

## SWINE bulk import: does it pay?

`swine_xcmp.py` pairs functions by name: 99 names that occur once in swinedecomp's
`reccmp-functions.csv` (SWINE HD addresses) and in our mapping (Panzers HD addresses). It
compares **SWINE original against Panzers original**. Both were built with VS2015, so
compiler noise is mostly gone, and the score answers "if we copy the SWINE body, how close
is it to Panzers?". `ours_vs_pz` is our current lift against Panzers, for comparison.

| group | pairs | median SWINE→Panzers | pairs ≥70% | median ours→Panzers | SWINE beats ours |
|---|---|---|---|---|---|
| engine/UI (widgets, stream, properties, menus, terrain) | 86 | 43% | 16 | 60% | 26 |
| **gameplay (game/, world/)** | 13 | **23%** | **1** | 40% | **2** |

Gameplay pairs, looked at closely (feature diff of the two originals):

- **SUnit::ServerRefresh**: SWINE has 1889 instructions, 96 calls and a switch, and
  references `_glow%d`, `feher/sarga/piros`, `Akna` (mines). Panzers has 291 instructions,
  35 calls and no switch. Only 14 member offsets are shared (Jaccard 0.11). Score 4%. It's a
  different function under the same name.
- **SUnit::ExecuteCommand**: 299 vs 290 instructions and a switch in both, but 8 calls vs 42
  and 4 shared member offsets out of 79 (Jaccard 0.05). Score 6%: same role, rewritten body,
  different SUnit layout.
- **SWorld::LoadMap**: 642 vs 403 instructions, and the chunk tags and error strings differ
  ("Tilemap without Heightmap" vs "Unsupported map file version"). 3 member offsets shared.
  Score 28%.
- **STriggerCondition::Load**: 82 vs 101 instructions, and 7 of 10 member offsets shared
  (Jaccard 0.70). Score 73%. This is the one gameplay pair that really carried over.
- SUnit::EC_Follow 23% (0 shared offsets), SUnit::SetPosition 11% (30 vs 190 instructions),
  SWorld::Initialize 17%, SWorld::LoadDoodads 17%.

For comparison, shared widget code from the same compiler scores 75–94%. Examples:
SCheckBox::OnMouseDown 92%, SFileSystem::ReadFile 94%, SSliderH::OnTimer 83%.

**Verdict:** bulk-importing SWINE `game/` and `world/` and then fixing it would not pay off.

- In 11 of 13 gameplay pairs the SWINE original is further from Panzers than our current lift
  is.
- Even the struct offsets don't carry over, because the classes have different layouts. A
  copied body would have to be rewritten field by field against the HD disassembly, and
  that is the work we already do.

This matches the M2 estimate that 3–6% is reusable. Import pays only for leaf engine/UI code.
There, 16 of 86 pairs are ≥70% SWINE→Panzers and 26 beat our current body, which suggests
re-basing those 26 on the SWINE body (for example SMesh::CreateIndexBuffer, SArchiveStream
helpers and the SCheckBox/SSlider handlers). The useful workflow: run `swine_xcmp.py` for a
candidate before copying, and copy only when it scores ≥70%.

## Not verified

- The name-based SWINE pairing assumes that our Panzers names correspond to SWINE's. The
  Panzers names are our own guesses. A name collision on unrelated code (for example
  `SWidget::CaptureMouse`, 21 vs 2 instructions) gives a low score that doesn't mean a
  rewrite. I didn't run a name-free BSim search.
- The 326 markers without a PDB body (inlined or folded) aren't scored. Their code is inside
  the callers' scores.
- /OPT:ICF folds identical bodies. reccmp may then show another function's name for the same
  code (for example `SPanzersSquadMemberUnit::MarkBlockMap` for `SBuildingUnit::MarkBlockMap`).
- The Ghidra extents are from auto-analysis. A function with a non-returning tail call can be
  cut short.
- None of the triage above was confirmed at runtime. It comes from reading the disassembly and
  the source.
- effectschema.cpp isn't UTF-8, and reccmp skips it when scanning the sources.
